# 每层文件怎么写

## AGENTS.md —— 项目宪法

**七要素**（缺一不可）：项目概述 / **命令** / **完成定义（DoD）** / 项目结构 / 代码约定 / 边界禁区 / 当前阶段。

> AGENTS.md 社区实践公认：**「命令」和「完成定义」是价值最高、也最常被漏掉的两节**。
> 漏了命令，agent 会猜命令；漏了 DoD，agent 会凭感觉宣布完成。这两条必须写。

**另加三块地基**（2026-09-12 补，缺了规范只解决一半问题）：**会话启动** / **技能路由** / **主线锚定**。
详见 SKILL.md 同名章节。判断依据很朴素——问三个问题：

1. 新 agent 进场，知不知道**先读哪些文件**？（启动）
2. 它知不知道**这个项目该调用哪些技能**？（路由）
3. 它会不会**跑到主线之外**？（锚定）

### 会话启动节

放在**第 0 节**，开门见山。三行就够，关键是**记忆层写成探测链而非写死路径**。

**为什么不能写死**：**工具专属**的记忆（`.claude/`、IDE 会话缓存）是
**某个工具提供的能力，不是项目自带的文件**。写死路径 = 把规范绑死在那个工具上，
换 agent 就指向空目录。**本文件必须自足：没有记忆层，也得能让人把活干对。**

写法：

```md
2. **找记忆**——按序探测，命中即读；全都没命中就执行 2.4（不要报错、不要停下来问）：
   1. {项目内的记忆目录，如 `.workbuddy/memory/`}：长期结论 + 最近一篇日志
   2. `docs/项目记忆.md` / `PROGRESS.md` / `NOTES.md`（项目自带的通用记忆文件）
   3. `CLAUDE.md` / `.claude/` 等**工具专属**记忆
   4. **全都没命中 → 由你建立项目记忆载体**：新建 `docs/项目记忆.md`，写下本次结论与坑，
      并在本文件 §0 登记它的路径。**已有可用的载体就不要重复创建。**
```

四条硬要求：

1. **区分两类记忆**：**项目内**的（`.workbuddy/memory/`、`docs/项目记忆.md`）
   躺在仓库里，用**相对路径**写，换任何 agent 都能读到；**工具专属**的（`.claude/`）才需要探测。
2. **必须写「都没有怎么办」，而正确动作是「自己建一个」**——不是跳过、更不是停下来问。
   不写这一句，agent 遇到空目录就卡住了。
3. **命中即停，不重复创建**。已有可用载体还再建第二份，双写必然漂移。
4. **探测链是示例不是清单**，换环境时加一行即可，不要重写第 0 节。

#### 坑的归宿：AGENTS.md

用户原话（2026-09-12）：「**坑一定得记下来，避免下次再犯。这是必须要记下来的。**」

| 载体 | 性质 | 换工具后 |
|---|---|---|
| 工具记忆层 / 会话日志 | 过程，带日期带试错 | 可能读不到 |
| 项目自带的 `docs/项目记忆.md` | 半持久，项目内 | 一般能读到 |
| **`AGENTS.md` 的「已知坑」节** | **结论，跟着仓库走** | **永远在** |

**所以：坑在写进记忆层的同时，也必须沉淀进 AGENTS.md「已知坑」。**
这决定了「已知坑」节不是可选装饰，而是本技能产出物里**优先级最高的一节**。

### 技能路由表

| 列 | 写什么 | 反例 |
|---|---|---|
| 遇到这件事 | **场景**，用户会说的那种话 | 「硬件移植」——这是功能，不是场景 |
| 调用技能 | 真实存在的技能名 | 编一个听起来合理的名字 |
| 什么时候加载 | 时点，标它在主线上的位置 | 空着 |

**筛选标准是「整个项目周期内会不会用到」，不是「现在用不用得上」，也不是「我装了什么」。**
规范是按项目全周期立的，所以第 10 阶段才用的技能只要真会用到，就该写进来；
「什么时候加载」列只标明它是主线上第几步，**不是过滤条件**。

反过来说：装了二十个技能、只要"可能有用"就全塞进去，等于没有路由表——
判断句式：「在这个**项目周期**里，遇到 X 场景，我会不会想叫它？」答否才删。

**条目多了就分组**（主链路 / 规范维护 / 后期阶段），比平铺好读。

### 主线锚定

### 主线锚定

一条铁律就够：**不在 todo 清单上的新工作，先补清单再动手。**
配合给出 todo 的绝对路径 + 声明它是唯一清单。这是防偏离唯一能机械执行的手段。

### 写法要点

- **命令**必须是能直接跑的原样字符串，含端口、flag。
  - 好：`python src/server.py` → http://127.0.0.1:8788
  - 坏：`启动服务`
- **边界写"禁止"不写"建议"**。
  - 好：「禁止直接改 `src/db/migrations/`，用 Alembic 生成」
  - 坏：「建议谨慎修改数据库迁移」
  - 理由：边界要能真正避免事故，偏好挡不住 agent。
- **用示例代替描述**。贴 5 行代码，胜过 100 字说明命名规范。
- **加自检步骤**：「完成前跑 lint + test」——让 agent 能自己验证。

### 完成定义（Definition of Done）· 单独成节，别塞进命令里

DoD 回答「怎么算做完」。必须是**可机械执行的检查清单**，不能是形容词。

- 按「改了什么」分组：改引擎怎么验 / 改服务怎么验 / 提交前怎么验 / 通用怎么验。
- 每条是**能跑出退出码的动作**，不是「确保正确」这种话。
  - 好：`python src/gen_daily_view.py` 退出码 0，且 `generated/每日视图.md` 时间戳刷新
  - 坏：功能正常，无报错
- **必须写「跑不了怎么办」**：上报卡在哪一步，禁止跳过检查直接报完成。
  不写这条，agent 会因为环境缺依赖而静默跳过全部检查。
- 引用具体路径和端口，别写「运行测试」——项目里往往不止一种验证方式。

### 已知坑（全文件最值钱的一节）

**它是"没有记忆层时唯一的经验靠山"。** 记忆层会随工具走掉，这一节跟着仓库走。

每条**三段齐全**，缺一段等于没写：

| 段 | 回答什么 | 反例 |
|---|---|---|
| 现象 | 看到什么（可观测的表现） | 「有时会出问题」 |
| 触发条件 | 什么时候会遇上 | 「不小心的时候」 |
| 怎么绕 | 具体动作，最好给命令 | 「注意一下」 |

用表格或列表都行，但**三段不能省**。只写现象不写触发条件，agent 无法预判；
只写触发条件不写怎么绕，agent 知道要来了却不知道怎么办。

**沉淀纪律**（把记忆层的水位维持住）：

```
记忆层日志（过程：带日期、带试错、带报错原文）
        ↓ 蒸馏
AGENTS.md「已知坑」（结论：现象 + 触发条件 + 怎么绕）
```

- **触发蒸馏的信号**：同一个坑在日志里出现**第二次** / 阶段切换 / 日志超过 30 天没整理。
  出现第二次尤其关键——说明它没被沉淀，才会重踩。
- 蒸馏时**只留结论不留过程**：报错原文、试错轮次可以砍，三段结论一个不能少。

### 子目录嵌套（monorepo / 多模块）

AGENTS.md 允许在子目录再放一份，**就近覆盖**：agent 处理哪个目录的文件，
就读离它最近的那份，子目录规则覆盖上层同名规则。

- 主文件放**全局通用**的：定位、命令、铁律、边界。
- 子文件只放**本包特有**的：本包的命令、本包的禁区、本包的术语差异。
- 子文件不重复上层——重复就会漂移，漂移比缺失更难查。
- 冲突优先级：**就近优先** > 显式对话指令 > 根文件。

### 常见错误

| 错误 | 为什么错 |
|---|---|
| 写"遵循最佳实践" | 等于没说。要具体到「SQL 必须参数化，禁止字符串拼接」 |
| 贴整本编码规范 | 抽 10 条关键的，详细文档单独链出去 |
| 依赖/命令不更新 | 比没有更糟，agent 会一直生成错代码 |
| 混入工具专属配置 | 跨工具的放 AGENTS.md，专属的放原生文件 |
| 缺 Definition of Done | agent 凭感觉宣布完成，是返工的头号来源 |
| 一个文件越写越长 | 超 200 行就该拆子目录 AGENTS.md，不是继续加长 |

### 工具兼容层（CLAUDE.md 等）

主流工具（Codex / Copilot / Cursor / Gemini CLI / Windsurf / Devin / Aider / Zed / goose）
**原生读 AGENTS.md**。唯一例外是 **Claude Code**：它自动加载 `CLAUDE.md`，不原生读 AGENTS.md。

80/20 实务做法：

1. 80% 的指令写在 `AGENTS.md`，作为唯一真相源。
2. 需要支持 Claude Code 时，建 `CLAUDE.md`，内容只写一行 import（如 `@AGENTS.md`）。
   **不要复制粘贴内容**——复制就会漂移，两周后两份文件必然不一致。
3. 只有工具专属能力才写在工具专属文件里。

> 要不要建兼容层：只有你一个人、只在一个工具里用，就不用建。

### 长度控制

官方社区建议：**100-200 行以内**，只放导航性信息，细节链出去（渐进式披露）。
本技能分档更细：小型 <80 行，中型 <250 行，大型 <500 行。

**超过就拆子目录**（用嵌套 AGENTS.md），不要用加长主文件来解决。

## CONTEXT.md —— 术语表

### 格式

```md
**术语**
一两句话定义「是什么」，不写「做什么」。
_Avoid_：同义词1、同义词2、同义词3
```

### 规则

- **只收项目特有概念**。通用编程词（配置、缓存、路由、超时）一律不收，哪怕用得多。
  判断标准：换个项目这个词还成立吗？成立就不收。
- **绝不掺实现细节 —— 这是最容易犯的错**。CONTEXT.md 是术语表，不是 spec、不是草稿纸、
  不是实现决策的收容所。以下四类一律写到 `AGENTS.md` 去：

  | 违规写法 | 为什么不行 | 该去哪 |
  |---|---|---|
  | 「判定条件：`publish: ready` 或 `reviewed: true` 且有四平台分节」 | 这是判定逻辑，会随代码变 | AGENTS.md 代码约定 |
  | 「写在源 md 的 frontmatter `publish` 字段」 | 字段位置是实现细节 | AGENTS.md 代码约定 |
  | 「配置在 `config/`，默认 7 天」 | 路径与默认值是实现细节 | AGENTS.md 配置段 |
  | 「由 `gen_daily_view.py` 在每日 09:30 生成」 | 模块名与调度是实现细节 | AGENTS.md 命令段 |

  **自检**：把这条术语给一个不懂代码的领域专家看，他看不懂就说明混进了实现细节。
- **有主见地选一个词**，其余列进 `_Avoid_`。模棱两可等于没定。
- **定义"是什么"**，不写"做什么"。
  - 好：`registry` —— 记录每条内容处于状态机哪一格的派生表
  - 坏：`registry` —— 用于存储和查询内容状态
- 概念多了用二级标题分组。

### 用法

写完要真的执行：agent 输出里出现 `_Avoid_` 里的词，就是 drift，要改回来。
遇到表里没有的词，只有两种可能——生造了不该用的说法，或确实有缺口（补进表）。

## docs/adr/ —— 架构决策记录

### 四段（少一段就不叫 ADR）

1. **Context** —— 当时面对什么约束、什么数据、什么痛点
2. **Decision** —— 选了什么
3. **Alternatives Considered** —— 至少 2-3 个，每个写 Pros/Cons/Rejected 理由
4. **Consequences** —— 包括代价，不只写好处

### 规则

- **先匹配项目已有约定**：目录位置、编号方式、章节标题，跟已有 ADR 保持一致，不要另起一套。
- **不删除旧 ADR**。决策变了就写新的，标注 `Superseded by 000X-简短描述`（引用的是文件名，不是 `ADR-XXX` 形式）。
- **Context 被推翻也要标注，哪怕 Decision 还有效**（最容易漏的一条）。决策整个作废时大家会写新 ADR；
  但**做法没错、只是当初的理由说错了**这种情况，没人会回去改——于是后人照着错误的 Context 推理，
  整条弯路重走一遍。在文首加：
  ```md
  > ⚠️ **本文 Context 已被新事实推翻**（YYYY-MM-DD）：{新事实一句话}。
  > Decision 仍然有效，但勿据此 Context 推理。
  ```
  实例（智能设备项目 ADR 0004）：Context 写"屏幕左边缘像素落在可视区外"，后查明是
  **面板四角圆角**啃掉贴边内容；"串口可调"的 Decision 完全正确，就一直没人改 Context。
- **写不出三个 Alternatives 就不是决策**，只是随手选的，别硬凑 ADR。
- 命名：`0001-简短描述.md`，四位序号，不重启编号。

### 从哪迁移

不要凭空编。从这些地方挖：

- README 的「设计原则 / 铁律 / 护栏」章节
- 项目记忆类文档的「演进时间线」「关键决策」表
- git 提交信息里的重大变更

## tasks/todo.md —— 任务清单

### 任务结构

```md
## Task N: 标题
**Acceptance criteria:** 可验证的条件
**Verification:** 跑什么命令 / 手动看什么
**Dependencies:** 依赖哪个任务
**Estimated scope:** S(1-2文件) / M(3-5文件)
```

### 规则

- **唯一目标文件**。不要散落多个 todo，不要同时用 GitHub Issues 又写 todo.md。
- **不覆盖未完成的任务清单** —— 那些可能正在另一个会话里做。
- **垂直切片**，不要水平：
  - 好：任务1=用户能注册（schema+API+UI 一条龙）
  - 坏：任务1=建全部表，任务2=写全部 API
- **每 2-3 个任务一个 Checkpoint**。
- **粒度 S/M**。L 以上必须拆；agent 在 S/M 上表现最好。
- 任务标题里出现「和 / 并且」= 其实是两个任务。

## CONSTRAINTS.md —— 质量门槛（大型）

**必须有数字**，因为 prose 约束 agent 会忽略，数字能被机械检查。

- 覆盖率下限、性能预算（首屏 ms / 包体积 KB）、允许的超时
- **Floor Guard**：无论如何不可突破的底线（不得新增 `@ts-ignore`、不得跳过测试、不得删断言）
- 每条约束写清：阈值 + 谁来查（CI / pre-commit）+ 违反怎么办

用途：agent 会为了"跑绿"而降低标准（屏蔽 lint、跳过测试、删断言）。
带数字并机械校验的门槛，是唯一能挡住这件事的东西。
