# 接力机制与非破坏合并

> 2026-09-14 新增。思路借鉴自开源技能 `project-flow-cy`（CY-CHENYUE，GPL-3.0），
> 但**载体与规则按本技能的硬约束重写**：不绑 Claude Code / Codex、不依赖 hook、
> 不引入 `flow/` 目录，全部落在本技能既有的 `docs/` + `tasks/` 结构里。
> 本文只记**细则**，原则见 SKILL.md 的「收尾 = 交接棒」与硬约束 8–11。

---

## 1. 接力载体

### 为什么是「一个 append 文件」

多 agent / 多任务线 / 多终端跑同一个项目时，彼此不共享对话，唯一接口是**项目内的文件**。
载体的三种候选：

| 候选 | 问题 |
|---|---|
| 一天一个日志文件（`.workbuddy/memory/YYYY-MM-DD.md`） | 越攒越多，进场先猜读哪份；且**多半在工具专属目录里，换工具就消失** |
| 一张张交接卡 | 堆爆目录，且没有"哪张是最新的"的机械判据 |
| 覆盖式快照（每次重写 `CURRENT.md`） | 丢历史，事后没法回看"两周前为什么这么定" |
| **单一 append 文件，新的放最上面** | ✅ 留全历史 + 不堆目录 + **顶部即当前棒** |

落点：`docs/进展.md`（项目内、相对路径、换任何工具都在仓库里）。
首次创建直接复制 `assets/PROGRESS.template.md`——模板里带用法说明与并发规则，留在文件末尾。
**模板只留 assets 里那一份**，本文不重复贴，避免两处漂移。

### 交接条六件套

| 字段 | 要求 |
|---|---|
| 做了什么 | 事实，不写评价 |
| 为什么 | 这一棒的动机 |
| 怎么理解 | 判断依据 / 心智模型，**不是过程复述** |
| 产出 | 真实路径，多个就列多个 |
| 问题 → 解决 | 踩了什么、怎么绕的 |
| 下一步 | **接手方第一个动作**，具体到能直接执行 |

### 三条硬规则

1. **只带指针 + 增量。** 给路径不给内容。重抄的那一刻起，它就和源文件开始漂移。
2. **写完贴回对话。** 落文件是给下一个 agent，贴回复是给此刻的用户。只写文件 = 用户不知道你留了什么。
3. **「下一步」必须是可执行的第一个动作。** 写"继续推进"等于没写；写"跑 `python tools/preflight.py` 看第 3 项是否还红"才算。

### 与「已知坑」的分工（别合并成一份）

| | `docs/进展.md` | `AGENTS.md`「已知坑」 |
|---|---|---|
| 性质 | 过程，带日期带试错 | 结论：现象 + 触发条件 + 怎么绕 |
| 谁读 | 下一个 agent 进场第一件事 | 任何人干活前扫一眼 |
| 会不会删 | 不删 | 定期蒸馏，只留结论 |

一次收尾写**两处**：坑的结论进 AGENTS.md（上了保险），这一棒的过程进进展日志（保留"为什么"）。

### 多任务线并行时的并发

两条线同时 append 同一个文件会互相覆盖。**解法按优先级**：

1. **错峰写**：每条线只在**自己这一棒结束时** append 一次，不要边干边记。
2. **先读后写**：append 前先读回顶部两条，确认自己的条目没把别人的挤掉。
3. **并行期分流**：并行期间各自写自己的任务卡（`tasks/Txx-*.md`），
   进展日志只在**汇合点**写一条。任务卡是并行的，进展日志是串行的。

## 2. 非破坏合并（brownfield 接入已有项目）

### 动手前先列清单

把三样列给用户，确认后再写：

- **项目边界判断**（单体 / 单仓多子项目 / 多独立仓库）
- **将创建 / 修改的文件**
- **明确不会创建、不会移动的内容**（已有 README、子项目文档、构建产物）

为什么必须写第三条：用户怕的不是你加东西，是怕你**动他已有的东西**。

### 标记块注入

往已有 `AGENTS.md` 补内容时，全部塞进标记块：

```md
<!-- project-constitution:start -->
...本技能维护的内容（会话启动 / 技能路由 / 收尾交接 / 目录地图）...
<!-- project-constitution:end -->
```

- 已有该块 → 只更新块内，块外一个字不动
- 没有块 → 追加到文件末尾（不改用户原有章节顺序）
- **永远不要**把模板整份覆盖上去

### 冲突三级

| 情况 | 动作 |
|---|---|
| 文件不存在 | 直接建 |
| 存在且是本技能注入的（有标记块 / 内容可比对） | 更新块内 |
| 存在但不是本技能的（用户自己的内容） | **生成 `xxx.suggested.md` 请用户确认**，不硬改 |

JSON / YAML 配置同理：能结构化合并就合并；解析失败或结构不明 → 出建议文件，不猜。

> 真实的并发事故（2026-09-13）：项目被多个会话同时编辑，提交时把别人的在途改动一起提交了。
> 所以**清单 + 确认**不是流程洁癖，是防事故。

## 3. 项目边界判断（monorepo 不重复建控制层）

**不要按文件夹数量判断。** 按 `.git` / workspace 配置 / 构建与发布方式判断。

| 形态 | 判据 | 控制层怎么建 |
|---|---|---|
| 单体项目 | 一个构建入口、一套发布节奏 | 根级一套 |
| 单仓多子项目 | 前端 / 后端 / 落地页共享同一仓库与总体目标 | **根级一套**；子项目只补局部入口 |
| 多个独立仓库 | 子目录有独立 `.git` / 版本 / 发布 / 团队边界 | 各自一套，上层只记跨仓目标与契约 |

排除目录：`node_modules/`、`dist/`、`build/`、临时目录、普通工具目录——这些**不是子项目**。

### 局部入口写什么（`<module>/AGENTS.md`）

只写四样：**本模块职责 / 本模块命令 / 本模块约束 / 指回根级**。
**不写总体计划、不复制根级决策、不另建控制层。**

已有子项目 README、生成文档、必须紧贴代码的说明**留在原地**，
只在根级 `docs/README.md` 加索引。不要为了集中而搬家。

## 4. 与 project-flow-cy 的差异（为什么这几条没抄）

同原理、不同载体。记录取舍，避免以后来回改：

| 他的做法 | 我们为什么不照抄 |
|---|---|
| `flow/` + `docs/` 双目录 | 本技能已有 `docs/` + `tasks/`，再引 `flow/` 就是第二套控制层，违反「一个边界一个控制面」 |
| `.hooks/stop-doccheck.sh` 强制收尾 | 依赖 Claude Code / Codex 的事件级 hook。WorkBuddy 的 automation 是**定时**不是**事件**，撑不起"每回合结束"的语义。理念（把 prose 变机制）认，实现不可移植 |
| `CLAUDE.md` 软链到 `AGENTS.md` | Windows 建软链要管理员权限，且 git 对软链处理不一致。**用一行 import 复制版更稳** |
| 跨模型评审当质量门 | 理念好（审稿模型 ≠ 产出模型），但本机只有一个模型入口。列为**可选增强**，不写进硬约束 |
| `flow/decisions.md` 散记录 | 本技能已有 `docs/adr/` 四段式 + 三条件准入，更严，不降级 |
| 有 evals / shell 自测 | 值得学，但本技能产出是**文档**不是代码，暂无可跑的断言面 |

**真正从他那里吸收的**：单一 append 交接日志、六件套字段（含"下一步"）、
写完贴回对话、只带指针 + 增量、一个边界一个控制面、非破坏标记块、动手前先列清单。
