# Context Budget · 规范越写越长怎么办

规范文件建好只是开始。项目迭代几轮后，AGENTS.md 会膨胀、ADR 会堆积、
todo 会变成历史档案——然后 agent 又开始抓不住重点。**分层结构需要配套的预算纪律。**

---

## 75% 法则

**上下文窗口用到 75% 就开始裁，别等满。** 满了才处理，模型注意力已经碎片化，会出现断崖式质量下跌。

---

## 砍什么 / 保什么

| 内容 | 何时砍 |
|---|---|
| 失败的尝试与其报错 | 已经解决了就砍，只留结论不留过程 |
| 冗长工具输出（find 结果、全量文件列表） | 提取完信息立刻砍 |
| 来回讨论 | 决策一达成就砍 |
| 被替换掉的旧代码草稿 | 替换的瞬间砍，当前文件才是记录 |

| 内容 | 保到最后 |
|---|---|
| 原始任务定义与关键约束 | 全程 |
| 正在调试的报错 / 失败的测试输出 | 全程 |
| 正在编辑的文件及其最新版本 | 全程 |
| 任何被要求强制执行的硬约束（权限规则、命名约定） | 全程 |

---

## 压缩优于删除

删之前先压成一句话，保留结论：

```
压前：[8 条消息调试一个 import 报错 —— 各种尝试、错误日志、死路]
压后："import 问题定位到 src/lib/db.ts 循环依赖 —— 已把共享类型移到 src/types/index.ts 解决。"
```

细节没了，决策还在。真需要细节时，这句话是重新排查的面包屑。

---

## 排序：稳定的在前，活动的在后

模型对开头和结尾记得最牢，中间最差（lost-in-the-middle）。所以：

```
← 会话开始                                        生成点 →
[背景：规则、规范、架构]      [进行中：当前文件、报错、任务]
```

**这条直接影响规范文件的组织方式**：AGENTS.md 里稳定的铁律放前面，变动的"当前阶段"放后面。

---

## 分层加载的执行纪律

规范分了层，就得真的按层加载，不能每次全塞：

- 第 1-2 层（AGENTS.md / CONTEXT.md）—— 每次必读
- 第 3 层（ADR）—— **只读与当前任务相关的那一条**，不要 ls 完整个目录全读
- 第 4 层（todo）—— 只读当前阶段那一节，不要读完整历史
- 第 5 层（源码）—— 单次控制在 2000 行内

> 典型错误：「这是我们的 ADR 目录」然后把 15 条全贴进去。

---

## 四个反模式

| 反模式 | 症状 | 修法 |
|---|---|---|
| 上下文饥饿 | agent 发明不存在的 API、无视约定 | 开工前加载规范文件 + 相关源码 |
| 上下文洪泛 | 塞了 >5000 行无关内容，agent 反而跑偏 | 只给当前任务相关的，目标 <2000 行 |
| 上下文陈旧 | agent 引用已删除的旧模式 | 大切换时开新会话 |
| 静默困惑 | 该问的时候瞎猜 | 明确列出冲突选项让用户选 |

---

## 规范文件自身的保鲜

规范腐烂比没有规范更糟——agent 会照着过时的规则生成错误代码。

**触发更新的时机**（不是定期，是事件驱动）：

- 重大架构决策落地 → 立刻写 ADR
- 依赖变了 → 立刻改 AGENTS.md 命令段
- 出现新术语 → 立刻补 CONTEXT.md
- 阶段切换 → 立刻更新 todo 与「当前阶段」

**每次提交前问一句**：这次改动让哪个规范文件失真了？
