# Brownfield Playbook · 项目中期补规范

> 绝大多数真实场景不是"新项目开工前"，而是"项目已经跑了一段，现在才想起来该有套规范"。
> 本手册处理这种**存量接入**。与 greenfield 的根本差别：**不能凭空设计，只能考古。**

---

## 为什么中期补规范反而更有效

早期写规范是在猜——你不知道项目会长成什么样，写出来的多半是废话。
中期写，决策已经发生、矛盾已经暴露、真实约束已经显形，写下来的是**有证据的东西**。

中期接入的额外收益，是它能**顺手把历史遗留问题照出来**。
实测（action-cockpit，2026-09-08）：为补 AGENTS.md 而做的探测，一次性发现了 4 个此前没人注意的问题——
依赖未声明、README 目录树过时、文档自相矛盾、自动化路径写死。

## 考古清单（按顺序扫，不要跳）

| # | 挖什么 | 去哪挖 | 产出 |
|---|---|---|---|
| 1 | 设计原则 / 铁律 / 护栏 | README 的对应章节 | `AGENTS.md` 铁律 + 边界 |
| 2 | 演进决策 | 「项目记忆 / 时间线 / 关键决策」类文档、表格 | `docs/adr/` 候选 |
| 3 | 重大变更 | `git log --oneline` 全部提交信息 | ADR 候选 + 提交风格 |
| 4 | 真实依赖 | **grep 源码 import** | `AGENTS.md` 命令与依赖段 |
| 5 | 真实命令 | `__main__` 入口 / Makefile / CI / scripts | `AGENTS.md` 命令表 |
| 6 | 真实结构 | `ls` 各目录 | `AGENTS.md` 结构树 |
| 7 | 迭代轮次 | 带 v1/v2/v3 后缀的原型或配置文件 | 当前阶段判定 |
| 8 | 路线图 | README 路线图章节 / TODO | `tasks/todo.md` |

### 无 git 项目怎么考古（很常见，别卡在这）

上表第 3 项假设有 `git log`。**没有 git 的项目照样能考古**，只是证据源换成这四样：

| 替代证据源 | 挖什么 | 说明 |
|---|---|---|
| **记忆层 / 项目日志** | `.workbuddy/memory/*.md`、`CLAUDE.md`、带日期的进展笔记 | 最值钱——里面常有"为什么踩坑"的过程记录，git log 反而没有 |
| **文档时间戳与文件名** | `*_20260906_*.bin`、带日期的备份/导出文件 | 从命名反推决策发生的时间点，用来回填 ADR 的真实 Date |
| **文档内部的日期** | ADR 的 `Date`、todo 的「最后核对」、日志里的日期 | 串联出时间线 |
| **遗留问题表** | 已有 todo 里的「遗留问题 / 已知坑」 | 直接就是 ADR 与铁律的候选 |

代价要说清楚：**改动无版本历史、误改不可回滚**。所以无 git 项目必须多做两件事：

1. 在 `AGENTS.md` 的 Git 工作流节**显式写明**「本项目未建 git，改大文件前先手动备份」，
   不要删掉这一节假装没有——agent 默认以为有版本控制，会放心大胆地改。
2. 把「建议 `git init` 一次」记进遗留问题表，交给用户决定。

## 铁律：文档与实况冲突时，以实况为准

**README 是最容易过时的文件**，因为它写完后就没人同步了。

实测冲突（action-cockpit）：
- README 与项目记忆都写「零外部依赖、仅 stdlib」
- 但 `src/server.py` 实际 `import uvicorn / fastapi / pydantic`
- 且仓库无 `requirements.txt`

**处理方式**：不要静默沿用 README，也不要擅自改 README。
在 `AGENTS.md` 里显式标注冲突：

```md
> ⚠️ README 与 docs/项目记忆.md 中「零外部依赖、仅 stdlib」的描述**已过时**，
> 那是对阶段 1 的描述，不适用于 src/server.py。
```

然后把「README 过时」记进 `tasks/todo.md` 的遗留问题表，**带证据行号**，交给用户决定是否修。

## 阶段判定

中期项目的"当前阶段"不能问用户一句话了事，要从证据推：

| 证据 | 说明 |
|---|---|
| `git log` 提交数量与密度 | 3 个 commit = 早期；几十个 = 中期 |
| 原型文件 v1→v4 | 迭代了 4 轮，说明该阶段反复打磨中 |
| 路线图勾选状态 | ✅ / ⏳ / 📋 直接给阶段 |
| 配置文件数量增长 | 新 config 出现 = 进入新阶段 |

判定后写进 `AGENTS.md` 的「当前阶段与下一步」，并**在 todo 里标出进行中的任务**。

## ADR 回填规则

历史决策的 ADR 要**用真实日期回填**，不要写成今天。

- `Date` 填决策实际发生的日期（从 git 提交时间或文档记载取）
- `Context` 必须引用当时的真实约束与数据，不能事后美化
- `Alternatives Considered` 如果当时真没考虑过替代方案，就写实际的替代路径（例如"换一个统一 App"这种被否掉的方向），**不要编造一个从没讨论过的方案充数**

先写 1-2 条最关键的（通常是"为什么选这个架构"和"为什么不那么做"），其余标 TODO。
空目录比假 ADR 好。

---

## 增量而非重写

中期项目已经有人在用了。补规范时：

- **不重写已有文档**。AGENTS.md 是新增的，README / 项目记忆保持原样。
- **不删除任何东西**。冲突只做标注。
- **不擅自修复遗留问题**。只记录 + 给证据 + 给建议。
- **已有的 `tasks/todo.md` 若存在且未完成，绝不覆盖**——那些可能正在另一个会话里做。

## 中期接入自检

- [ ] 所有命令都实际验证过能跑（不是从 README 抄的）
- [ ] 依赖来自 grep 源码，不是来自 README
- [ ] 至少发现并记录 1 个历史遗留问题（通常会有 3-5 个）
- [ ] 每处文档冲突都在 AGENTS.md 里显式标注了
- [ ] ADR 用的是真实历史日期与真实约束
- [ ] todo 反映了真实的进行中任务，不是理想化的计划
- [ ] CONTEXT.md 里没有任何实现细节（判定条件、字段名、路径都不行）
